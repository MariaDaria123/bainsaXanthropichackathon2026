# How the swarm works: documentation and provenance

This file explains the system that produced the p4 c6 ("Beyond the boundary") results: what ran, which rules it followed, and how to trace any claim back to the agent, prompt, critic reports and git commit that produced it.

- **What happened, as data:** `SWARM_LOG.md`, regenerated by `python tools/swarm_report.py`.
- **Event:** BAINSA × Anthropic hackathon "Climbing to the Frontier", track Proof Pursuit, 26 Sep 2026.
- **Team:** Iuse, Ianis, Maria, Afonso.

---

## 1. What it is, in one paragraph

Several Claude Code agents run in parallel on four team laptops (plus a cloud workspace) and attack one open problem. They coordinate only through this git repository, which acts as a shared blackboard. It holds a queue of tasks, one folder of results per task, and an append-only log of findings. Every task follows the same research loop:
1. An **author** agent tries to disprove the claim, tests lemmas on small cases, then proves or computes.
2. **Two blind critic** agents referee the write-up independently.
3. A claim keeps a strong label ([PROVED], [BOUNDED], [COMPUTED]) only if both critics return `VERDICT: ACCEPT`.

The worker program enforces rule 3, not the agents. Findings flow back onto the board, where every later agent reads them. Agents also propose follow-up tasks, so the queue grows toward whatever is working.

## 2. Architecture

```
            GitHub repo (the blackboard)
  swarm/tasks/{open,claimed,done}/*.json   task queue
  swarm/board/<worker>.jsonl               findings, one append-only file per worker
  swarm/results/<task-id>/                 result.md, notes.md, findings.jsonl, critic reports, code
        ▲  git pull / commit / push (claims are atomic: a rejected push = someone else won)
        │
  ┌─────┴─────┬───────────┬───────────┬───────────┬──────────────┐
  Iuse        Ianis       Maria       Afonso      cloud workspace
  (a)×2       (a)+(c)     (b)×2       (c)×2       proof/compute tracks only
  each worker: own clone in ~/swarm-workers/<name>, loop = claim → author → 2 critics → publish
```

- **Coordinator:** `swarm.py`, about 500 lines of Python with no server. Workers poll the repo.
- **Agents:** headless `claude -p` sessions. Each one is a fresh context, so an agent knows only what the prompt and the repo tell it.
- **Directions:** each task is tagged (a), (b) or (c), after the three routes the cell allows. Laptops use `--match "(a)"` and similar to stay on one route. Follow-up tasks inherit the tag.

## 3. The research loop inside one task

| Step | Who | What | Enforced by |
|---|---|---|---|
| 1. Claim | worker | Takes the highest-priority open task in its direction; moves it to `claimed/` and pushes. A rejected push means the race was lost, so it picks another. | git |
| 2. Brief | worker | Builds the prompt: exact cell text, task goal, track rules, author method, and the board split into **FACTS** (passed 2 critics), **FAILED** (never retry without something new) and **OPEN** (conjectures and observations to attack). | `build_prompt` |
| 3. Author | agent | Balanced start (try to disprove first); test lemmas by script before proving; write `result.md` with every claim labelled, `notes.md` (dead ends, hidden from critics) and `findings.jsonl`. Time box 25 min. | prompt + session timeout |
| 4. Critics | 2 agents, in parallel, fresh | Blind: read only `result.md`, the cell and the cited code. Statement check first, then every step, then run the code. Each ends with `VERDICT: ACCEPT / MINOR / RESTART`. | `critic_gate` |
| 5. Fix round | agent | On MINOR: one author round fixes every listed point, then both critics review again. | `critic_gate` |
| 6. Label gate | worker | Strong labels survive only with ACCEPT + ACCEPT. Otherwise they are downgraded to [CONJECTURED], keeping the original label in `claimed_status`. RESTART adds a `dead_end` finding with the critic's stated reason. | `finish` (fail-closed) |
| 7. Publish | worker | Appends findings to `swarm/board/<worker>.jsonl`, turns `new_task` findings into new tasks, moves the task to `done/`, and pushes. | git |

**Epistemic labels** (defined in `CLAUDE-cell-6-open.md`):

| Label | Meaning |
|---|---|
| [PROVED] | Full proof |
| [BOUNDED] | A rigorously proved bound, even if not tight |
| [COMPUTED] | Exhaustive exact, interval, SAT or Z3 verification up to K, with code under 10 min |
| [CONJECTURED] | A precise statement with evidence but no proof |
| [OBSERVED] | A pattern in data, not yet a precise statement |

## 4. Where the method comes from

| Element | Source |
|---|---|

| Blackboard coordination through git; atomic claims | Built for this hackathon (`swarm.py`) |

## 5. Rules every agent was given

- **Exact statement, never weakened.** A special case must be labelled as one.
- **Proof-grade computation:** exact (int, Fraction) or interval arithmetic, runs under 10 minutes, and for p4 searches the full 5-part certificate (`tools/cert.py`, `tools/rerun.py`).
- **Citing ≠ proving:** a published argument counts only if written out in full and checked. Gaps found in published proofs are reported as findings.
- **A computation beats an argument:** if a script contradicts a claim, the claim is refuted.
- **No hand-waving:** "clearly", "WLOG", "by symmetry" and similar are banned unless the argument is given.

## 6. How to trace any claim (provenance)

1. Find the claim on the board (`python swarm.py board --problem p4`) or in `SWARM_LOG.md`. Each finding records `worker`, `task`, `t` (time), `status`, `claimed_status` and `critic`.
2. Open `swarm/results/<task>/`:
   - `result.md`: the argument as submitted to the critics.
   - `critic_1_roundN.md`, `critic_2_roundN.md`: the referee reports and verdicts.
   - `notes.md`: what the author tried and abandoned.
   - scripts and data: rerun them.
3. Open `swarm/tasks/done/<task>.json` for the exact task goal, who created it (human or a parent task), when it was claimed and finished, and the final critic summary.
4. Run `git log --follow swarm/results/<task>/result.md` for the exact commit and time it was published.
5. Rebuild the exact prompt: `swarm.py:build_prompt()` at that commit, plus the board as it stood (`git show <commit>:swarm/board/...`).

## 7. Known limitations (be honest about these in the write-up)

- **The gate is strict, and early on it cost us results.** In the first round, all three finished tasks ended MINOR/MINOR after one fix round. Every lemma claimed as proved was downgraded to [CONJECTURED], even though the critics judged the approaches sound. These are near-proofs, not failures.
- **No web access in the cloud workspace.** Cloud workers could not fetch papers, so literature tasks were requeued for the laptops. Cloud workers ran only proof, compute and search tracks.
- **Critics are the same model family as the author.** Independence comes from fresh context and blindness to the author's notes, not from a different model. An optional Gemini third opinion was available by hand.
- **Agents may misread literature.** Every literature finding carries its fetched URL; anything unfetched is tagged unverified.
- **Human interventions:** starting and stopping workers, adding tasks, and requeueing tasks are all visible in the git log as commits not made by a worker.
